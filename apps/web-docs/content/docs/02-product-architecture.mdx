## 2.1 Enterprise Product Architecture Overview

SmartZen is architected as an event-driven modular monolith with strict domain boundaries, separating data ingestion, verification pipelines, capability inference, and demand-side matching. The system balances ultra-low read latencies with asynchronous, fault-tolerant background execution.

## 2.2 Organizations & Multi-Tenancy Architecture

SmartZen implements a **Row-Level Multi-Tenant Isolation Model** within a unified PostgreSQL database, reinforced by application middleware and database Row Level Security (RLS).

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       MULTI-TENANT DATA ISOLATION                           │
├──────────────────────────────────────┬──────────────────────────────────────┤
│ INSTITUTIONAL TENANTS (Universities) │ CORPORATE TENANTS (Employers)        │
├──────────────────────────────────────┼──────────────────────────────────────┤
│ • Tenant ID: inst_univ_123           │ • Tenant ID: corp_tech_789           │
│ • Enrolled Student Scoping           │ • Recruiter Team Seats               │
│ • Departmental Cohorts (CSE, IT)     │ • Corporate Job Requisitions         │
│ • Internal Placement Drive Rules     │ • Active Recruitment Pipelines       │
└──────────────────────────────────────┴──────────────────────────────────────┘
                                  │
                                  ▼
      ┌────────────────────────────────────────────────────────┐
      │             GLOBAL TALENT GRAPH & PRIVACY SHIELD       │
      │ • Candidates retain immutable identity anchor.         │
      │ • Profiles remain ANONYMIZED until candidate opts in.  │
      │ • Employers access profiles strictly via shared drives.│
      └────────────────────────────────────────────────────────┘
```

### Multi-Tenancy Invariants:

1. **Tenant Foreign Key Binding:** Every tenant-scoped entity (`StudentProfile`, `JobRequisition`, `ApplicationRecord`, `AssessmentSession`) maintains an indexed, immutable `tenantId` / `organizationId` foreign key.
2. **Prisma Middleware Isolation Filter:** Application-level Prisma middleware automatically intercepts every query, injecting `{ where: { tenantId: request.tenant.id } }` into all database operations. Cross-tenant reads are structurally rejected before reaching the SQL engine.
3. **PostgreSQL Row Level Security (RLS):** As a defense-in-depth barrier, PostgreSQL RLS policies enforce `USING (tenant_id = current_setting('app.current_tenant_id'))`, guaranteeing isolation even if application-layer filters are misconfigured.
4. **Candidate Privacy Shield:** Candidates own their underlying talent identity. When an employer queries the global talent graph, matching queries operate on anonymized vector representations. Personal Identifiable Information (PII) is only unlocked when the student or university TPO explicitly forwards the dossier into that employer's active pipeline.

## 2.3 Handling Mid-Flight Changes & Assessment Persistence

A critical requirement of an enterprise assessment platform is handling **mid-flight deployments, container restarts, and candidate network dropouts** without disrupting active examinations.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    MID-FLIGHT SESSION PERSISTENCE FABRIC                    │
├─────────────────────────────────────────────────────────────────────────────┤
│ 1. CANDIDATE TAKES EXAM                                                     │
│    Client sends answer: POST /assessments/submit                            │
│    Headers: Idempotency-Key: uuid-1234, Session-Token: sess-abc             │
│                                  │                                          │
│ 2. ATOMIC REDIS COMMIT           │                                          │
│    Answer & timestamp written to Redis Hash: assessment:sess-abc:drafts     │
│    Heartbeat recorded: assessment:sess-abc:last_seen = UnixTimestamp        │
│                                  │                                          │
│ 3. SERVER-AUTHORITATIVE TIMER    │                                          │
│    BullMQ delayed job scheduled at test start: timer-expire:sess-abc        │
│    Does NOT rely on client device clock or active container process.        │
│                                  │                                          │
│ 4. BLUE-GREEN DEPLOYMENT OCCURS  │                                          │
│    Caddy shifts traffic to Green container.                                 │
│    Blue container drains active HTTP keep-alive connections over 30s.       │
│    Next answer submission routes seamlessly to Green container.             │
│    Green container reads state from shared Redis; candidate notices zero lag│
└─────────────────────────────────────────────────────────────────────────────┘
```

### 1. Server-Authoritative Timer Persistence

- Candidate assessment durations are never tracked via client-side JavaScript timers (which can be paused, manipulated, or lost on browser crash).
- Upon test initialization, the system registers a delayed job in **BullMQ** with `delay = testDurationSeconds * 1000`.
- The job is persisted in Redis. If the application server restarts, crashes, or is upgraded via Blue-Green deployment, the Redis-backed BullMQ job remains intact.
- When the timer fires, a background worker marks the session as `SUBMITTED_TIME_EXPIRED` and triggers automated BARS rubric evaluation.

### 2. Idempotent Answer Submissions

- Every client answer submission carries a client-generated UUIDv4 `Idempotency-Key`.
- If a candidate experiences a Wi-Fi drop or cellular handover during submission, the client retries the request automatically.
- The API checks Redis for `idempotency:{key}`. If already processed, the API returns the cached HTTP 200 response immediately, preventing duplicate answer recording or double penalty.

### 3. Graceful Connection Draining (Zero-Downtime Deployment)

- During production updates, `scripts/blue-green-deploy.sh` spins up the standby container environment and verifies health via `GET /health` (`status: UP`).
- Caddy's active upstream configuration is reloaded atomically (`caddy reload`).
- The retiring container enters a **30-second graceful drain phase**: it stops accepting new HTTP connections while allowing existing in-flight candidate requests and streaming WebSocket defense connections to complete cleanly.
- Once the drain window expires, the old container is gracefully stopped (`docker compose stop`).

## 2.4 Scalability Architecture & Sizing

SmartZen is engineered to run high-density workloads efficiently on a **Single High-End Linux VPS** (16 vCPUs, 64GB ECC RAM, NVMe storage) with a verified 12-factor migration bridge to AWS.

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      CAPACITY & RESOURCE ALLOCATION                         │
├─────────────────────────┬───────────────────────┬───────────────────────────┤
│ COMPONENT               │ RESOURCE BUDGET       │ OPERATIONAL ROLE          │
├─────────────────────────┼───────────────────────┼───────────────────────────┤
│ Caddy Reverse Proxy     │ 1 vCPU, 512MB RAM     │ Edge TLS 1.3, Rate-limit  │
│ Active API-Core (NestJS)│ 4 vCPU, 8GB RAM       │ Synchronous API handling  │
│ Standby API-Core        │ 0 vCPU (idle/swapped) │ Blue-Green deployment     │
│ BullMQ Async Workers    │ 4 vCPU, 8GB RAM       │ AST parsing & LLM rubrics │
│ PgBouncer Pooler        │ 1 vCPU, 512MB RAM     │ 2,000 : 20 connection pool│
│ PostgreSQL 16 + pgvector│ 4 vCPU, 24GB RAM      │ Shared-buffers 16GB, HNSW │
│ Redis 7.2 Sentinel      │ 2 vCPU, 16GB RAM      │ Session state, BullMQ     │
└─────────────────────────┴───────────────────────┴───────────────────────────┘
```

### PgBouncer Connection Pooling:

- Node.js / NestJS applications create multiple connection pools. Without connection pooling, 5,000 concurrent candidate sessions can exhaust PostgreSQL's `max_connections` (causing fatal `FATAL: remaining connection slots are reserved for non-replication superuser connections`).
- SmartZen deploys **PgBouncer** in `transaction` pooling mode:
  - Application services connect to PgBouncer on port `6432`.
  - PgBouncer handles up to **2,000 concurrent client connections** while holding only **20 persistent connections** to PostgreSQL.
  - Server connection overhead drops from ~10MB per client process to virtually zero, maintaining PostgreSQL memory efficiency.

### 12-Factor Cloud Bridge to AWS:

All platform services adhere to 12-factor cloud-native principles:

- Environment parity: Configuration isolated via strict `.env` variables.
- Stateless processes: Zero local disk dependency; all assets stored in S3/MinIO.
- Clean AWS Migration Path: The architecture maps 1-to-1 with AWS managed services:
  - PostgreSQL 16 -> Amazon RDS Aurora PostgreSQL
  - Redis -> Amazon ElastiCache for Redis
  - BullMQ Workers -> AWS ECS Fargate Autoscaling Task Groups
  - MinIO -> Amazon S3 with CloudFront CDN

# System Architecture & Topology

HireKiwi's backend is architected as a high-performance **modular monolith**, implemented in NestJS 11 and Fastify (`apps/api-core`).

All modules run inside a single unified process, share an in-memory execution context, and are deployed via Docker Compose onto hardened, dedicated High-End Linux VPS servers behind Caddy and Cloudflare.

## Single High-End VPS Deployment Model & Blue-Green Engine

HireKiwi is deployed on a dedicated, high-performance Linux VPS instance (Ubuntu 24.04: 32 vCPU, 128 GB RAM, NVMe storage), running both Production and Development in strictly isolated Docker Compose networks:

| Environment     | Deployment Slice                             | Public Domain         | Zero-Downtime Traffic Routing                                                         |
| :-------------- | :------------------------------------------- | :-------------------- | :------------------------------------------------------------------------------------ |
| **Production**  | `hirekiwi-prod-blue` & `hirekiwi-prod-green` | `hirekiwi.online`     | Caddy dynamic upstream switches between Blue and Green upon passing `/health` checks. |
| **Development** | `hirekiwi-dev`                               | `dev.hirekiwi.online` | Dedicated compose project with isolated database volumes and dev app ports.           |

### Blue-Green Zero-Downtime Switchover Protocol

1. New production builds deploy to the currently inactive color (e.g. Green).
2. Database migrations are applied forward-only via `prisma migrate deploy`.
3. Automated health probes verify `http://127.0.0.1:3010/health` and `/ready`.
4. Caddy upstream shifts 100% of live traffic to the new color via `caddy reload` with zero connection drop.
5. In-flight requests drain safely before the inactive slot is powered down.

### Cloud-Readiness & Scheduled AWS Migration

The entire deployment adheres strictly to 12-factor cloud principles:

- Containerized workloads run independently of host-specific binaries, with each service built via its own isolated Dockerfile (`apps/<app>/Dockerfile`).
- Compose topologies are decoupled: local development leverages lightweight data plane orchestration (`docker-compose.dev.yml`), while VPS environments leverage the full multi-slot topology (`docker-compose.prod.yml`), enabling targeted service rollouts and granular scaling without touching untouched containers.
- Externalized environment configuration (`DATABASE_URL`, `REDIS_URL`, `KAFKA_BROKERS`, `S3_ENDPOINT`) enables zero-code-change migration directly into **AWS ECS Fargate, AWS RDS PostgreSQL (Multi-AZ with pgvector), AWS ElastiCache Redis, and AWS MSK**.

## Bounded Module Contexts

Each module inside `apps/api-core/src/modules/*` maintains strict domain encapsulation:

- **`auth`**: Stateless 15-minute JWT verification, 7–14 day HttpOnly refresh rotation, and SAML 2.0 / OIDC institutional SSO.
- **`assessment`**: Assessment attempt lifecycle, Redis session caches (`session:assessment:{id}`), and BullMQ server-authoritative timeout jobs.
- **`sandbox`**: Non-networked Docker container execution for student code snippets with 256MB RAM caps and 5-second hard timeouts.
- **`ai-gateway`**: Centralized LLM gateway managing Anthropic Claude 5 Sonnet with automatic fallback to Google Gemini 2.5 Pro / Flash.
- **`placement`**: PostgreSQL `pgvector` semantic matching between student profiles and incoming job descriptions.
- **`certificate`**: HMAC-SHA256 signature hashing, QR payload generation, and PDF credential compilation.

## Standalone Proctoring CV Sidecar (`apps/proctoring-cv`)

The only standalone microservice in the architecture is `proctoring-cv`. Written in Python 3.12 using OpenCV and MediaPipe, it processes periodic webcam snapshot frames to verify single-face presence, gaze direction, and candidate liveness without streaming full-bandwidth video.
